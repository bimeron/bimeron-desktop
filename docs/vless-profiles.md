# VLESS profiles

The Add profile dialog accepts a complete `vless://` URI and stores it as the sole `[AccessKey] VLESS` source. Its fragment suggests the profile name. The visual editor can edit the URI source and explicit `Type = vless` parameters. The raw editor remains available for configurations outside the visual editor. The selected Core CLI's `validate` command is authoritative; the GUI does not reimplement VLESS transport validation.

Explicit VLESS settings cover TCP with TLS or REALITY (Vision is supported only with REALITY), WebSocket with TLS, gRPC with TLS or REALITY (including authority and TunMulti), and XHTTP with TLS or REALITY in the core's supported modes. XHTTP over HTTP/3 is selected by `ALPN = h3` with TLS and no fingerprint. The GUI leaves core to validate combinations and details such as custom gRPC method paths. One access-key source is written at a time. The connection contract uses the validated profile's absolute path through the existing `start` RPC and follows the core's reported session state. Connection controls and regular polling are currently disabled by the [navigation baseline](navigation-spec.md); the criteria below describe the required connection behavior when restored.

Extended XHTTP settings (`XHTTPExtra` and separate `XHTTP...` option fields) are edited in Raw config under the shared [preservation rules](profile-preservation.md). When an explicit VLESS profile contains settings the visual form cannot represent, switching to Raw config must keep the original text, and saving from the visual form must be blocked. Editing Raw config is the explicit way to save such a profile. URI sources remain unchanged on save; the VLESS tab decodes supported URI parameters into disabled fields for inspection, including gRPC `mode=multi`, WebSocket early data encoded in `path`, and masked XHTTP `extra`.

Acceptance criteria:

- Adding a valid VLESS URI, including an IPv6 server or encoded fragment, creates a `.conf` accepted by a VLESS-capable core. Invalid links are rejected by `core validate` without exposing credentials in diagnostics.
- Opening and saving VLESS URI and explicit profiles retains their source and all fields represented by the visual editor. Extended settings are never removed by switching tabs or saving; the user must use Raw config for intentional changes. Unedited saves retain the original bytes. Raw requires an explicit Show/Edit action.
- The visual form represents the supported TCP, WebSocket, gRPC and XHTTP combinations listed above. `core validate` rejects invalid combinations. Existing Shadowsocks and SOCKS5 profiles continue to work.
- A service without VLESS support may reject `start` even when the bundled CLI validates a profile. The GUI reports the service error and its authoritative state; installing a VLESS-capable service is required to connect.

Desktop source version 0.2.0 includes VLESS import and editing. The current bundle pin is published Core `v0.2.0-beta.1`, revision `6e0c171505be8e349d5f42570f7ceb3e50ac6697`, which supports VLESS. Historical candidate and VM results do not establish connectivity of the current Desktop baseline. See the [integration contract](core-desktop-integration-contract.md) for exact baselines, preservation requirements and the distinction between CLI validation, installed service support and runtime evidence.
