# Signed core service updates

## Specification

Since Bimeron Desktop 0.1.2, the installed Windows or Linux core service can update independently of the desktop package. The package's bundled core remains the bootstrap and recovery copy. The running service's `hello.core.version`, not the bundled file, is the installed version. Desktop, core, IPC, and profile-format versions are independent.

The updater implements IPC protocol `1` and profile format `1`. Published core `v0.1.0-beta.5` has reviewed GUI bounds `gui_min: "0.1.5"` and `gui_max_exclusive: "0.1.6"`, so GUI `0.1.5` can consider it when beta updates are enabled. Older published core `v0.1.0-beta.3` has bounds `[0.1.0, 0.1.2)` and remains ineligible for GUI `0.1.5`.

The GUI checks the public `bimeron/bimeron-core` GitHub Releases at startup and periodically, and can check on demand from Settings. Checks and downloads are quiet. Stable is the default channel; beta releases are considered only when the user enables beta updates. A missing signing key, no signed compatible release, network failure, or a malformed release never triggers an unsigned fallback. A build configured with an empty key says "Signed updates are not available yet" and does not run the legacy bundled-core `service update` command.

For each candidate release, fetch `update-manifest.json` and `update-manifest.json.sig`. Select a trusted Ed25519 public key by the manifest's `key_id` only as an untrusted lookup hint; verify the signature over the exact manifest bytes, including the final LF, before using any other manifest field. The signature is standard base64 of 64 bytes plus one LF. Reject unknown keys, unknown schema, malformed fields, duplicate or missing targets, unsafe asset names, `gui_reviewed: false`, absent GUI bounds, mismatched release tag/channel, and unsupported GUI, IPC, profile format, OS, or architecture. Select the newest compatible core version strictly newer than the running core. An unknown or development running version does not update automatically.

Download the selected ZIP from that release with size limits. Verify exact byte length and SHA-256. Read only the exact `<os>-<arch>/bimeron[.exe]` member, reject duplicate members and unsafe archive structure, and write the executable into a private temporary directory. Hash its bytes. Never extract other archive members or run an unverified binary.

Only after the archive is fully verified does the GUI offer "Update now" or "Later". The dialog warns that an active VPN is interrupted and the same profile is reconnected after a verified successful update. On confirmation, elevate only the core bundled beside the GUI and run `service update -source <absolute-staged-path> -version <core_version> -sha256 <executable-sha256>`. The downloaded executable is always data and is never launched by the GUI. Before elevation, require the GUI executable and bundled core to be protected from ordinary-user writes, the package directory to be protected, and ancestor directories to prevent replacement of any path component. Reject a writable or redirected package path. Probe the bundled core without elevation for the `-source` update protocol; an older bundled core requires a GUI package update. Keep the staged source alive through privileged command completion. The privileged helper copies the source into its protected service directory and verifies the copied hash, identity, and architecture before stopping the old service. It checks the replacement service through IPC `hello` and rolls back on failure. Show the result, refresh the service and IPC state, and then restore the previously active connection when the success conditions above hold.

### Connection restoration after a service update

At confirmation, remember the currently connected profile. Warn that updating interrupts VPN traffic and offer to reconnect it. After the helper succeeds, require IPC `hello` from the new service with the expected version and a disconnected status before starting that same profile. Do not reconnect after cancellation, helper failure or rollback, a mismatched version, or removal of the profile. A disconnected update does not start a connection. Keep the existing user setting for connecting when the GUI starts separate from this behavior.

Acceptance criteria: a successful update with an active profile reconnects that profile once after new-service verification; a disconnected update stays disconnected; failed, canceled, or mismatched updates do not reconnect. The GUI reports a failed reconnect through its normal connection status and log.

## Acceptance criteria

- Tests with a test key verify exact-byte signatures and reject tampering, unknown keys, invalid compatibility, duplicate targets, unsafe names, and wrong archive length/hash. The test key is never embedded in the production application.
- Both Windows architectures and both Linux architectures compile. A build explicitly configured with an empty key reports unavailability and cannot install a release.
- With a trusted production key, a protected bundled helper, and a suitable signed release, the GUI downloads quietly, prompts only after verification, elevates the bundled helper with the required `-source`, `-version`, and `-sha256` flags, and refreshes service state after completion.
- Existing unsigned releases cannot be installed. The bundled core is never used as an update candidate.
- No update path writes the desktop package payload; only a previously active profile is reconnected after verified success.
- A writable package directory or bundled core without `-source` disables direct service updates. The GUI never elevates the downloaded executable. Windows passes a quoted absolute source path intact, including spaces and quotes. Cancellation leaves the installed service untouched and removes the staged source.
- If the installed GUI or bundled core fails the protected-path check, the status explains that a protected system installation is required. If only the bundled helper lacks `-source`, the status asks for a GUI package upgrade. Neither condition starts an update.
- A source replaced after GUI verification or with the wrong digest is rejected by the privileged helper before service stop. Core-side tests cover IPC `hello` failure and rollback; GUI tests cover command construction and pre-elevation rejection.

## GUI package upgrade specification

The next GUI package version is `0.1.1`, giving Windows Installer and Debian a monotonic package upgrade from `0.1.0`. Preserve the MSI UpgradeCode and install directory. The MSI upgrade must replace the bundled `bimeron-core.exe` with the trusted helper without invoking `service update` or changing the installed service. The DEB upgrade must likewise replace `/usr/bin/bimeron-core` while preserving user settings and the service. A GUI installed in a user-writable directory still cannot run privileged core updates.

The ordinary package scripts pin published `v0.1.0-beta.5` and its four verified GitHub ZIP hashes. They must explicitly select `.tools/core` during configuration, replacing any cached local candidate override. An archive hash mismatch must stop packaging.

Acceptance criteria: the `0.1.1` MSI has the same UpgradeCode as installed `0.1.0`, a higher ProductVersion, and the trusted bundled core at the same path. A disposable Windows installation test must confirm the actual core file hash changes after the package upgrade. The `0.1.1` DEBs have the correct architecture, protected core path, and newer package version. Tests must show that a signed, reviewed temporary-key fixture accepts GUI `0.1.1` only when the signed compatibility bound includes it, while the signed unreviewed core candidate remains rejected.

Disposable Windows Sandbox results: the cached installed `0.1.0` MSI and both locally built replacement MSI versions returned exit code 0. Both `0.1.0` → `0.1.0` and `0.1.0` → `0.1.1` replaced `C:\Program Files\Bimeron\bimeron-core.exe` from SHA-256 `56d6aabf934daa6bfc66c3e11b284f473130e86c2182fd274a958ef8dffa3f3b` to `c3ba0e13bab976084935d32abc4dd71dcf65075c01a44bf7768fc5622f87d638`. ### Separate-installation test procedure

1. Create a disposable Windows or Linux installation, capture a snapshot, install GUI `0.1.0` and a running older core service, and record the GUI version, bundled core SHA-256, service executable SHA-256, IPC `hello` version, and VPN state. Keep VPN disconnected for the negative helper cases; connect it for the successful GUI update case.
2. Install GUI `0.1.1` as a package upgrade. Confirm that the package's bundled helper changes to published `ff489b8`, while the installed service executable and IPC `hello` version stay unchanged. Confirm the new helper is under a protected system path and the GUI rejects an otherwise identical copy under a user-writable path.
3. Verify that published `v0.1.0-beta.3` is signed by the pinned key `7370a2d8cf890e5e`, has `gui_reviewed: true`, and includes GUI `0.1.1` in its signed compatibility range. Enable beta core updates and use the GUI's Update action. Confirm quiet verification, the VPN warning, elevation of only the installed helper, CLI arguments, the new service version via IPC `hello`, and restoration of a previously active VPN after verified success.
4. Restore the snapshot for a wrong-digest case. Invoke the installed trusted helper on a staged, valid target executable with its correct version but a deliberately wrong `-sha256`; confirm a nonzero exit before service stop and unchanged service file hash and IPC `hello`. This tests the privileged boundary directly and does not substitute an unsigned release into the GUI.
5. Restore the snapshot for an IPC failure case. Core must provide a valid target build that passes privileged source identity, architecture, and digest checks but fails the new service's IPC `hello`. Invoke the trusted helper with the matching SHA-256. Confirm a nonzero result, the old executable restored, the old service running and answering `hello`, and VPN still disconnected. Keep the backup and report its path if rollback itself fails.

Any release used through the GUI in step 3 must have a valid signature from the pinned key. A test-only release source or fixture may be injected into automated tests, never into the production GUI. Run service-changing steps only during an approved maintenance window.

## Beta update setting lifetime

"Include beta core updates" starts unchecked on every application launch. Its state is held only in memory for the current process and applies to manual, startup, and periodic update checks. Older persisted `app/coreBetaUpdates` values are discarded. Exiting or restarting Bimeron resets the option to unchecked; stable update checks remain enabled.

Acceptance criteria:
- Enabling the checkbox lets all update checks in the current run consider beta releases.
- After quitting and relaunching, the checkbox is unchecked even if an older installation stored `app/coreBetaUpdates=true`.
- No update check reads the old settings key.
